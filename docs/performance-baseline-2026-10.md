# 性能計測：基準値と改善後（2026-10-09）

- 基準値：HEAD 8d54f5c（1.2.0 系）に計測プローブだけを入れたビルド。
- 改善後：c93c7ce＋その後の修正（エラー時・ベンド後の小節単位の復元、検証方法）。
- 生データ：`docs/perf-reports/baseline-8d54f5c.json`、`docs/perf-reports/after.json`
- 実行方法：`pnpm build && node scripts/perf-benchmark.mjs <label>`。比較は `node scripts/perf-summary.mjs a.json b.json`。
- 環境：Windows 10、Electron 41（dist を electron.exe で開く）。同じマシンで、基準値と改善後を同じスクリプトで続けて計測した。
- 譜面：
  - ①168小節×2トラック（4032音、既存の edit-performance-check と同じ）
  - ②合成600小節×8トラック（42600音、和音・16分・休符を含む。JSON では 40MB 上限を超えるため GP7 で読み込み）
- 指標：
  - handler：キー操作などのイベント処理の同期時間。入力が止まる時間。
  - settled：描画・MIDI・見えている SVG がすべて完了するまでの時間。
  - span：アプリ内部の区間（`src/perf.ts`）。
  - 値は中央値 / p95 / 最大。サンプル数は ① 40/24/12/10、② 20/12/6/5。

## 音声（B2）

| | ① 基準 → 改善 | ② 基準 → 改善 |
|---|---|---|
| 通常再生 5 秒のアンダーラン | 0 → 0 | 0 → 0 |
| メインスレッドを 1.3 秒ごとに 1 秒止めた再生 6.5 秒のアンダーラン | 0 → 0 | 0 → 0 |
| 上記の間のメインスレッドでの音声パケット処理 | 20 ms / 220 packets → **なし** | 55 ms / 220 packets → **なし** |

- 現行のバッファ（目標 65536 フレーム ≈ 1.4 秒）は大きいので、どちらの経路でもこの負荷では途切れなかった。直結経路では、音声データがメインスレッドを一切通らない。
- 改善後の別の計測回では、②の負荷再生で 1024 フレーム（約 23ms）のアンダーランが 1 回出た（再現性は未確認）。
- **音質は聴感確認が必要（ユーザー）**。GM 音源での再生、クリック音の各種類、シーク、ループ、曲の終わりを確認してほしい。

## 残っている重い操作

- ベンド・タイ・スライドなどリンクを作る編集、小節の挿入・削除、トラック操作、移調：今も全曲正規化と MIDI 再生成（② で 1.5〜2 秒）。小節内に限られる編集は、取り消しのとき小節単位で戻るようになった。次の段階は操作コマンド＋逆操作（計画 P3）。
- 読み込み直後の初回描画と MIDI 生成（② で midi.generate 約 0.5 秒）。
- **② は TG に保存できない**：TG 内の TabStudioProject（JSON の複製）が 40MB 上限を超える。ベースラインでも同じで、保存形式の判断が必要。

`docs/perf-reports/` の JSON を `node scripts/perf-summary.mjs docs/perf-reports/baseline-8d54f5c.json docs/perf-reports/after.json` に渡すと再表示できる。基準値の 600×8 には、`midi.generate` 約 553ms と `edit.normalize` 約 540ms が、編集 1 回ごとに含まれていた。
