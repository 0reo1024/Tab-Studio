# ASIO の小さいバッファで譜面とモニタが途切れる件(2026-10-17)

## 症状

ASIO・バッファ 64(1.33 ms)でプラグインを立ち上げて弾くと、処理落ちで譜面の音がぶちぶち切れ、演奏もできない。

## 実際の構成(一次データ)

- ASIO ドライバ:NeuralDSP Nano Cortex のみ(`HKLM\SOFTWARE\ASIO`)
- 設定(`live.json`):ASIO、バッファ 64
- 譜面の音:SFZ ギター(`standard-guitar.json` → UI Standard Guitar KSOP)
- モニタ:BIAS FX 2(WebView の `tabstudio-live-chain`)
- CPU:Ryzen 5 2600(6 コア 12 スレッド)。`SystemResponsiveness` = 20

## 計測方法

`crates/tabstudio-audio/examples/callback_bench.rs`(使い方は冒頭のコメント)。

- 実機の代わりに、ASIO の buffer switch と同じ周期で起きるスレッドから `Core::process` を呼ぶ。
- コールバックごとの処理時間をすべて記録する。判断は平均ではなく、p99.9 と最大で行う。
- 外部プラグインは、アプリと同じライブ用リンク(遅延 3 ブロック)でつなぐ。

## 結果

| 条件(64 フレーム、予算 1333 µs) | 中央値 | p99.9 | 最大 | 予算超え |
|---|---|---|---|---|
| GM 音源 8 トラック | 52 µs | 364 µs | 712 µs | 0 |
| GM 4 トラック + NAM / + BIAS FX 2 | 89 / 44 µs | 408 / 368 µs | 602 / 529 µs | 0 |
| **SFZ 1 トラック** | 194 µs | 677 µs | 835 µs | 0 |
| **SFZ 2 トラック** | 227 µs | 1490 µs | 1853 µs | 0.25 % |
| **SFZ 4 トラック** | 250 µs | 2497 µs | 3139 µs | **1.8 %** |

- **原因は SFZ 音源をデバイスのコールバック内で鳴らしていたこと。**
  - SFZ ギターは 1 トラックにつき弦ごとに最大 6 個の sfizz を持つ。64 フレームごとに全部を呼ぶので、1 回あたりの固定費が重い。
  - 和音の発音・消音の瞬間には、1 回で 2〜3 ms かかる。
- GM 音源、NAM、BIAS FX 2(既定プリセット)、スレッドプールは原因ではなかった。
  - プールのヘルパーを 0 にしても、結果はほぼ同じだった。
- 参考:全コアを埋める負荷をかけると、MMCSS「Pro Audio」のスレッドは約 2 ms 止まる。TIME_CRITICAL のスレッドは止まらない(`BENCH_PRIO=tc`)。

## 対策:譜面の音の先読み処理(engine.rs)

- 譜面側(曲・トラック・試聴・リバーブ・クリック・バッキング)は `Music` として専用スレッドで動かす。
  - スレッドの優先度は TIME_CRITICAL。
  - 256 フレーム単位で、デバイスより先に作っておく(最低 768 フレーム=16 ms、またはコールバックの 2 倍)。
- デバイスのコールバック(`Core`)は、出来上がった譜面の音をキューから取り出す。そこに楽器入力(NAM・プラグイン)を足し、マスターとリミッタをかけるだけにした。
- 再生位置とバッキングの位置は、キューに残っている分を差し引いて報告する。カーソルは聞こえている音と一致する(テスト `anticipated_song_reports_what_is_heard`)。
- キューを通っても音は変わらない。inline とサンプル単位で一致する(テスト `anticipated_music_is_the_inline_music_later`)。
- `TABSTUDIO_AUDIO_AHEAD=0` を指定すると、従来どおりコールバック内で処理する。
- キューが足りずに無音になったフレーム数は、楽器入力パネルに「譜面の音の欠け」として表示する(`live_status` の `drops.musicShort`)。

| SFZ 4 トラック・64 フレーム | 中央値 | p99.9 | 最大 | 予算超え | 譜面の欠け |
|---|---|---|---|---|---|
| 修正前(inline) | 246 µs | 2044 µs | 2495 µs | 1.1 % | — |
| **修正後** | **10 µs** | **43 µs** | **148 µs** | **0** | 0 |
| 修正後 + 全 12 スレッドに負荷 | 11 µs | 38 µs | 89 µs | 0 | 0 |
| 修正後 SFZ 8 トラック | 9 µs | 61 µs | 242 µs | 0 | 0 |

実機(Nano Cortex ASIO、バッファ 128)での自動チェックは次のとおり。

- `tauri-live-input-check`:処理落ち 0、プラグインの遅れ 0、譜面の欠け 0。
- `tauri-native-playback-check`:合格。

## 代わりに増えたもの

- 譜面側の操作(再生・停止・シーク・試聴)が耳に届くまで、16〜25 ms 遅くなる。カーソルと録音の時刻合わせは、この分を補正している。
- ギターのモニタ(入力 → プラグイン → 出力)の遅延は変わらない。

## まだ確かめていないこと

- 実機のバッファ 64 で、実際に弾きながら 60 秒以上使ったときの確認。パネルの「処理落ち」「プラグインの遅れ」「譜面の音の欠け」が 0 のままかを見る。
- 重いプラグインやプリセットでは、モニタだけが欠けることがある(「プラグインの遅れ」が増える)。その場合は、ライブ用リンクの遅延を自動で 1 ブロック増やす仕組みを入れる。

## 追記:プラグイン練習の遅延を詰める(同日)

### 遅延の内訳(実機 Nano Cortex、バッファ 64)

| 区間 | 値 | 変えられるか |
|---|---|---|
| 入力(ドライバ) | 2.8 ms | バッファを下げれば減る。ただし 32・48 では、このドライバのコールバックが 1 秒以内に止まった。64 が下限 |
| 出力(ドライバ) | 4.5 ms | ドライバ固定(どのバッファでも 4.5 ms) |
| 入力リングの待ち | 1.3 ms と表示していた | ASIO は同じ buffer switch で入出力するので、実際は 0。表示の数えすぎを直した |
| プラグイン経路(別プロセス) | 4.0 ms(3 ブロック固定) | ここを詰めた |

### 調べたこと

- 別プロセス方式のまま、リンクを 1〜2 ブロックに詰めた場合(callback_bench、BIAS FX 2、30 秒):
  - 1 ブロック:704 フレーム遅れた。
  - 2 ブロック:256 フレーム遅れた。
- ホスト側のスレッドを変えても、効果は小さかった。
  - TIME_CRITICAL:負荷時だけやや良かったが、無負荷では差がなかった。
  - スピン待ち:MMCSS の抑制を受けて、かえって悪化した。
- アプリ内(音声スレッド)で BIAS FX 2 を直接動かす場合を測った(`crates/tabstudio-fx-host/examples/process_bench.rs`、64 フレーム)。
  - 中央値 0.35 ms、p99.9 0.86 ms。
  - **最大は 2.8〜4.1 ms で、30 秒に 4〜6 回は 1 ブロックを超える。**
  - アプリ内で動かすと、これがそのまま出力全体の途切れになる。BIAS FX 2 では採用できない。
  - バッファ 128 でアプリ内にすると、ドライバ遅延だけで 13.7 ms になり、今より遅い。
- 軽いプラグイン(bx_greenscreamer)は、1 ブロックでも欠けなかった。

### 対策

- **リンク遅延の自動調整**(tabstudio-fxlink の EngineEnd)。
  - ライブ用リンクは 1 ブロックから始める。
  - 起動後 3 秒を過ぎてから、30 秒以内に 2 回遅れたときだけ 1 ブロック伸ばす。上限は 1024 フレーム。
  - 伸ばす処理は音声スレッド上で行う。1 回だけの長い停止(画面を開いた瞬間など)では伸ばさない。
- 伸びた値はプラグイン名ごとに `live-links.json`(アプリデータ)へ保存し、次回はその値から始める。
  - fx-host は link の返答で plugin 名を返すようにした。

### 結果(実アプリ、`LIVE_BUFFER=64 node --import tsx scripts/tauri-live-input-check.mjs 60 "BIAS FX 2"`)

| | プラグイン経路 | 表示の合計 |
|---|---|---|
| 以前(64、固定 3 ブロック + 待ち表示 1.3 ms) | 4.0 ms | 約 12.6 ms |
| bx_greenscreamer(128) | 2.7 ms(1 ブロック) | 16.3 ms(以前 21.7 ms) |
| BIAS FX 2(128) | 2.7 ms(1 ブロック) | 16.3 ms(以前 21.7 ms) |
| BIAS FX 2(64)1 回目 | 2.7 ms(2 ブロック) | **10.0 ms** |
| BIAS FX 2(64)2 回目 | 5.3 ms(4 ブロック、学習中の欠け多め) | 12.7 ms |

- BIAS FX 2 は、64 でどこまで詰められるかが PC の状態で揺れる(プラグイン自体の処理が、ときどき 3〜4 ms かかる)。
- 最も遅延が小さいのは NAM(エンジン内で処理し、リンクなし)で、64 では入出力の 7.3 ms だけになる。

### 遅延優先 / 安定優先(楽器入力パネルの「プラグイン」)

- 設定は live.json の `linkMode` に保存する。値は `latency` か `stable` で、既定は `latency`。
- **遅延優先**:1 ブロックから始め、30 秒以内に遅れが 2 回出たときだけ 1 ブロック伸ばす。
- **安定優先**:以前の固定値から始める(128 フレーム未満は 3 ブロック、128 以上は 2 ブロック。どちらも 128 フレーム以上)。遅れが 1 回でも出たら 1 ブロック伸ばす。
  - fxlink ヘッダの `grow` を `GROW_ANY` にして指定する。
- 学習した値はモードごとに保存する。`live-links.json` に「BIAS FX 2」「BIAS FX 2 [stable]」のように別々のキーで残る。
- モードを切り替えると、プラグインのリンクを作り直す。
- 実アプリ(バッファ 64、BIAS FX 2、40 秒)の結果:
  - 安定優先:3 ブロック(合計 11.3 ms)、欠けなし。
  - 遅延優先:学習中に 13 ms 分欠けて、3 ブロックに落ち着いた。
  - 確認コマンド:`LIVE_LINK_MODE=stable LIVE_BUFFER=64 node --import tsx scripts/tauri-live-input-check.mjs 40 "BIAS FX 2"`

## 追記:実測ベースの遅延表示とバッファ 32(同日)

### ループバック実測(Nano Cortex のヘッドホン端子 → 楽器入力、DI チャンネル 3)

計測コマンド:`live_probe engine --asio --buffer B --channel 3 --ping 10 --threshold 0.01`。どのバッファでも 10 回とも同じ値だった。

| バッファ | ドライバ申告(入力 + 出力) | 実測の往復 | 差 |
|---|---|---|---|
| 32 | 2.17 + 4.50 = 6.67 ms | 19.44 ms | 12.77 ms |
| 64 | 2.83 + 4.50 = 7.33 ms | 20.10 ms | 12.77 ms(613 フレーム) |
| 128 | 5.17 + 8.50 = 13.67 ms | 26.44 ms | 12.77 ms |
| 256 | 9.83 + 16.50 = 26.33 ms | 39.10 ms | 12.77 ms |

- ドライバが申告しない固定の 12.77 ms がある(USB 転送か、機器内部の処理)。
- 出力側の申告は、64 以下では 4.5 ms で下げ止まる。
- このため Nano Cortex を USB 経由で使う限り、往復 5 ms には届かない。32 にしても 64 から 0.66 ms しか縮まない。

### アプリの変更

- 「遅延を実測…」はクリックを 5 回出して中央値を取る。
  - 戻りの判定基準は、入力の雑音の 8 倍(下限 −50 dBFS、上限 0.2)。音量を絞ったループバックでも測れる。
  - テスト:`a_quiet_click_is_heard_above_the_inputs_own_noise_and_noise_alone_is_not`。
- 実測値からドライバ申告を引いた「隠れ遅延」を、機器ごとに `live-latency.json` に保存する。パネルの遅延表示は「実測:機器の往復 + 待ち + プラグイン」になる。
  - 未実測のときは「ドライバ申告・未実測」と表示し、合計には「以上」を付ける。
  - 実アプリ(バッファ 64、bx_greenscreamer)では、ボタンで 20.1 ms(ばらつき 0.0)を測り、表示は「合計 21.4 ms(実測:機器の往復 20.1 + プラグイン 1.3)」になった。
  - 確認コマンド:`LIVE_PING=1 LIVE_BUFFER=64 node --import tsx scripts/tauri-live-input-check.mjs 15`

### バッファ 32 が止まった原因

- 32 は単独なら 60 秒止まらず、途切れも処理落ちも 0 だった。16 も動いた。
- 48・96 は、ドライバが「hardware is malfunctioning」で拒否する(2 の累乗だけ受け付ける)。
- **止まった原因は、2 つのプロセスが違うバッファで同時に開いたこと。**
  - 64 で動いている最中に別プロセスが 32 で開くと、先に動いていた側のコールバックが 2.5 秒で止まった(15 秒中)。
  - 最初の調査時は、修正前の Tab Studio が 64 で開いていた。

## 追記:ASIO のバッファ一覧と、別のアプリにドライバを取られたとき(同日)

### バッファ一覧

- ASIOGetBufferSize の granularity が −1 のとき、ASIO SDK の定義では「2 の累乗」を意味する。
  - asio-sys はこれを「推奨値だけ」と読み違えている。cpal も最小・最大しか渡さない。
  - そこで device.rs から、asio-sys がリンク済みの関数を直接呼ぶようにした(`loaded_asio_sizes`、`asio_sizes`)。
- Nano Cortex は 8, 16, 32, 64, 128, 256, 512, 1024, 2048 を返した。パネルにはこの値だけを出す(`bufferChoices`)。
- 保存済みの値がドライバに受け付けられない場合(例:48)は、一覧に残したうえで「このドライバでは使えません」と表示し、選べないようにする。

### 別のアプリにドライバを取られたとき

- 同じドライバを別のプロセスが違うバッファで開くと、片方のコールバックが止まる。
  - どちらが止まるかは毎回同じではない。後から来た側が約 1〜1.5 秒で止まることが多い。
- アプリ側の判断:ASIO が 2 秒止まった時点でドライバが見えていれば(電源は入っている)、別のアプリに取られたと判断する。
  - 1 回目:取り戻して、「別のアプリが…一度止まりました。こちらに戻しました」と 30 秒表示する(`deviceNotice`)。
  - 15 秒以内にまた取られた場合:取り合いを避けて既定の出力に切り替え、説明と「もう一度つなぐ」ボタンを出す(`deviceTaken`、`live_reconnect`)。
  - 相手のアプリが終わると、既存の「戻ってきたら自動でつなぐ」処理で ASIO に戻ることもある。
- 確認:`scripts/tauri-asio-taken-check.mjs`(Nano Cortex の実機 + live_probe を 32 で起動する「別のアプリ」役)。
  - 再現しない回は、その経路を「再現せず」と記録する。
  - 実機で取り戻し、譲る、自動で戻る、の 3 つとも確認した。
