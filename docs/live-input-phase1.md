# 楽器入力(常時録音・プラグイン練習) フェーズ1 調査と設計メモ

2026-10-15。対象は Tauri とネイティブ音声エンジンのみ、Windows。計測は `crates/tabstudio-audio/examples/live_probe.rs` で行った(使い方は冒頭のコメントを参照)。

## 1. フェーズ1でやったこと

- **設定「楽器の入力を常に録音する」**(`liveRecording`)を追加した。既定はオフ。設定画面の「楽器入力」欄にある。
  - 録音とモニタ(プラグインを通して聴くこと)は独立させる。オフでもプラグイン練習はでき、録音リングにも書かない。
  - 録音処理はまだ無いので、**この設定はフェーズ2まで何も変えない**。
  - ネイティブ音声エンジンが無い環境(旧アプリやブラウザ)では、この欄を表示しない。
- 計測ツール `live_probe` を作った。サブコマンドは5つ。
  - `devices`:cpal から見えるデバイスと設定の一覧。
  - `wasapi`:WASAPI 自体が許す周期と、排他モードで使えるフォーマット。
  - `duplex`:入力→リング→出力の素通し。ドライバのタイムスタンプで遅延を見積もる。
  - `loopback`:出力したクリックを入力で検出し、実際の往復遅延を測る。
  - `fxlink`:外部 VST3 ホストの処理の戻り時間を測る。
- fx-host は現在のツリーで再ビルドしてから計測した。

## 2. 計測結果(この PC: Nano Cortex を入出力に使用、48 kHz)

### 2.1 デバイスと WASAPI

| 項目 | 値 |
|---|---|
| cpal のホスト | WASAPI のみ(`asio` feature 無効) |
| 共有モードの周期 | すべての機器で 480 フレーム(10 ms)。IAudioClient3 の最小値も 480 で、短くできない |
| 排他モードの最小周期 | 3.00 ms(全機器) |
| 排他モードで使えるフォーマット | Nano Cortex 入出力:16 bit と 24-in-32 bit PCM |
| ASIO ドライバ | 「NeuralDSP Nano Cortex」が登録済み |
| Nano Cortex の入力 | 「1+2」と「3+4」の2系統。どちらが DI(素の音)かは未確認。弾いて確認が必要 |
| VB-Audio Virtual Cable | ドライバはあるが有効なエンドポイントが無く、使えない |

### 2.2 入力→出力の素通し(cpal、WASAPI 共有)

`duplex --in "Nano Cortex (1+2)" --out "Nano Cortex (1+2)"` の結果:

| 区間 | 中央値 |
|---|---|
| 録音された時刻 → 入力コールバック | 0〜10 ms |
| リングでの待ち | 10 ms |
| 出力コールバック → 再生される時刻 | **31.9 ms**(cpal が WASAPI バッファを満杯まで先に書くため) |
| **合計(推定)** | **約 42 ms** |

- この推定にはドライバのタイムスタンプを使っている。AD/DA 変換や USB 転送の遅延は入っていないので、実際はこれより長い。
- `--buffer 128` を指定しても値は変わらない。共有モードの cpal はバッファ指定を無視する。
- フレーム数/秒が入力 47,967、出力 48,038 と食い違って見える。これは15秒間の開始・停止のタイミング差によるもので、クロックのずれではない(同じ機器なのでクロックは共通)。
- 出力の開始直後に、1056 フレームの不足(無音)が1回出た。

**実機での往復遅延は未計測。** 出力から入力に戻す経路(ケーブルか仮想ケーブル)が無く、`loopback` はクリックを検出できなかった。手順は §6 に書いた。

### 2.3 外部 VST3 ホスト(別プロセス・共有メモリ)の戻り時間

- **計測方法**:エンジン側は、本物のコールバックと同じ間隔で 20〜30 秒間ブロックを書き続ける。各ブロックについて「書いてから処理済みになるまで」の時間(戻り時間)を、遅れたブロックも含めて全部記録した。
- 計測側の送信の遅れは、最大 0.3 ms(1件だけ 1.6 ms)。測った遅延は、ほぼすべてホスト側のもの。
- 「Nブロック超」は、戻り時間がブロック N 個分を超えた件数。ライブ用リンクの遅延を N ブロックにしたら音が欠けていたブロックの数にあたる。

| プラグイン | ブロック | 編集画面 | MMCSS | 中央値 | p99.9 | 最大 | 1 / 2 / 3 / 4 ブロック超 |
|---|---|---|---|---|---|---|---|
| bx_greenscreamer | 128 (2.67 ms) | 閉 | なし | 0.05 ms | 0.43 | **9.14** | 3 / 2 / 1 / 0(7448 中) |
| bx_greenscreamer | 128 | 開 | エンジン側のみ | 0.06 ms | 0.36 | 4.28 | 2 / 0 / 0 / 0 |
| BIAS FX 2 | 128 | 閉 | なし | 0.43 ms | 0.90 | 1.10 | 0 / 0 / 0 / 0 |
| BIAS FX 2 | 128 | 開 | エンジン側のみ | 0.48 ms | 1.81 | **13.32** | 5 / 3 / 2 / 1 |
| BIAS FX 2 | 64 (1.33 ms) | 閉 | エンジン側のみ | 0.37 ms | 0.88 | 4.55 | 8 / 2 / 1 / 0(14949 中) |
| **BIAS FX 2** | 128 | **開** | **エンジン+ホスト** | 0.46 ms | 0.95 | **1.70** | **0 / 0 / 0 / 0**(11198 中) |
| **bx_greenscreamer** | 128 | 閉 | **エンジン+ホスト** | 0.06 ms | 0.32 | 1.14 | **0 / 0 / 0 / 0** |
| **BIAS FX 2** | 64 | 閉 | **エンジン+ホスト** | 0.36 ms | 0.75 | 2.86 | 4 / 1 / 0 / 0(22449 中) |

- 「ホスト」側の MMCSS は、ホストのリンクスレッドを MMCSS「Pro Audio」にする試験的な変更で測った。計測後に元に戻してある。製品に入れるのはフェーズ3。
- BIAS FX 2 は既定プリセットのまま測った。重いアンプやキャビネットを組むと処理時間は増える。
- 今のリンクの固定遅延は `fxlink::LATENCY` = 2048 フレーム(**43 ms**)で、設計上そうなっている(計測で決まる値ではない)。この遅延があるので、どのケースでも無音化は 0 だった。
  - 旧版の計測で一度だけ出た無音 1088 フレームは、計測方法を直した後は再現していない。

## 3. 分かったこと

1. **cpal の共有モードのままでは、目標の 10 ms に届かない。** 推定で約 42 ms かかる。原因は大きく2つ。
   - 出力バッファを 32 ms 先まで埋めている。
   - 共有モードの周期を 10 ms より短くできない。
2. **排他モードの WASAPI なら 3 ms 周期が使える。** 見積もりは、入力 3 ms + 出力 3〜6 ms + 変換・USB で、往復 **約 8〜12 ms**。未検証。
   - 欠点:排他中は、ブラウザなど他のアプリがその出力機器を使えない。
   - Nano Cortex の場合、フォーマットは 24-in-32 bit 整数にする必要がある。
3. **ASIO でも 10 ms 前後は狙える**(Nano Cortex に ASIO ドライバがある)。ただしビルド環境に次の2つが要る。
   - Steinberg の ASIO SDK(要ダウンロード、利用規約あり)
   - LLVM/libclang(cpal の `asio-sys` が bindgen を使う)。この PC には `clang` も `LIBCLANG_PATH` も無い。
4. **プラグインを別プロセスにしても、ライブ用途に足りる。ただしホスト側の優先度を上げることが前提。**
   - 通常の優先度のままだと、ホストのリンクスレッドがときどき 9〜13 ms 止まる(軽い bx_greenscreamer でも起きる)。数秒に1回、音が欠けることになる。
   - ホストのリンクスレッドを MMCSS「Pro Audio」にすると、最悪値は 1.1〜2.9 ms に下がった(BIAS FX 2 で編集画面を開いていても 1.7 ms)。
   - 128 フレームのブロックなら、リンク遅延 **2ブロック(5.3 ms)** で欠けは 0。64 フレームなら **3ブロック(4.0 ms)** で 0(22449 ブロック中)。
   - 同期型(遅延 0、そのブロック内に戻るのを待つ方式)は、MMCSS ありでも欠けが残るので採用しない。
   - **結論:プロセスは分けたままにする**(プラグインが落ちてもアプリを巻き込まない)。ホスト側の MMCSS と、ライブ用の短い遅延モードを足す。
   - 30 秒程度の計測なので、長時間の安定性はフェーズ3の8時間テストで確かめる。
5. **プラグイン遅延の補正は、ライブモニタでは使えない。** 今のリンクは、出力をプラグイン遅延分だけ前に書いて、43 ms の余裕の中に隠している。
   - 遅延を短くしたライブモードでは、入力より先に出力を出すことはできない。
   - ライブモードでは補正をせず、プラグイン遅延を**合計遅延に足して画面に表示する**。
   - 録音側の時刻合わせ(DI と鳴った音の位置を揃えること)は、その遅延を差し引いて行う。
6. **遅延の合計(見積もり)**:WASAPI 排他(3 ms 周期)で約 8〜12 ms。外部 VST3 を通すと、そこにリンク遅延 4〜5.3 ms とプラグイン自体の遅延が加わる。
   - NAM だけ(エンジン内で処理)なら 10 ms 前後に収まる見込み。
   - 外部 VST3 を通すと **13〜17 ms** になる見込みで、目標の 10 ms を少し超える。
   - 10 ms を厳守するなら、練習時だけ VST3 を同じプロセスで動かす選択肢を残す。ただしプラグインが落ちるとアプリも落ちる。

## 4. 設計

### 4.1 構成

```
[入力デバイス] → 入力コールバック ─┬→ 録音リング(DI、モノラル f32、5分)──→ 書き込みスレッド → ディスク(RF64、追記)
                                    │      ※ liveRecording がオフのときは書かない
                                    └→ モニタ経路:入力ゲイン → NAM / 外部 VST3(ライブ用リンク)→ 出力ミックス
[出力コールバック] ← 譜面再生(既存エンジン)+ モニタ + メトロノーム
```

- 入力は新しく `input.rs` に置き、デバイスとは独立したスレッドにする。入出力の受け渡しは rtrb の SPSC リングで行い、リングに溜まる量の上限は2ブロックにする。デバイスのクロックのずれは、溜まりすぎたら捨て、足りなければ無音を足す方法で吸収する。
  - 入出力が別々の機器でずれが続く場合だけ、フェーズ3で緩い再サンプリングを入れる。
- オーディオコールバックの中では、メモリ確保・ロック・I/O をしない。今の `output.rs` と同じく統計は atomic で取る。テストでは `assert_no_alloc` で確認する。

### 4.2 録音(フェーズ2)

- 対象はプラグイン前の DI。入力チャンネルの1本(選択式)を mono f32 で録る。48 kHz で5分なら **57.6 MB**(ステレオなら 115 MB)。
- 鳴った音(プラグイン後)も残すかは、フェーズ2で選択式にする。
- メモリ上のリングとは別に、書き込みスレッドが 1 秒単位でディスクにも追記する。
  - 形式は RF64/WAV。ヘッダは 5 秒ごとに書き直すので、落ちても直前までは読める。
  - 一時領域は app-data の `live/`。使用量に上限を設け(例:2 GB)、古いものから消す。
- 「保存」を押すと、遡った N 分(最大5分)に加えて、押した後も止めるまで1ファイルにつなげる。保存したテイクには、時刻・入力機器・プラグイン名・プリセットを JSON で添える。
- 録音中は画面に常に表示し、ワンクリックで止められるようにする。`liveRecording` がオフのときは、リングもディスクも使わない。

### 4.3 モニタ(フェーズ3)

- 優先度の高い順に、出力バックエンドを3つ用意する。
  1. **WASAPI 排他モード**(自前実装、`windows` crate):3 ms 周期で、入出力とも 24-in-32 bit。
  2. **ASIO**:cpal の `asio` feature を使う。SDK と libclang が揃った場合のみ。
  3. 今の cpal 共有モード:常に使える代替。約 40 ms と画面に明示する。
- 外部 VST3 にはライブ用リンクを足す。`fxlink` の遅延を可変にし、既定の 2048 はそのまま残す。ライブ用の遅延は、128 フレームのブロックなら 2ブロック、64 フレームなら 3ブロックとする。
  - スキップ処理も、可変になった遅延を参照するよう直す。
  - ホスト側のリンクスレッドを MMCSS「Pro Audio」にする。
  - プラグイン遅延は補正せず、表示に回す。
- 往復レイテンシの実測を画面から実行できるようにする(ループバックケーブルを使うウィザード)。

## 5. 判断してほしいこと

1. 低遅延の方式:
   - **(推奨)まず WASAPI 排他モードを自前で実装する。** 追加のダウンロードが要らない。
   - 先に ASIO を入れる。SDK のダウンロードと LLVM のインストールが要る。
2. 排他モードでモニタしている間は、他のアプリの音がその機器から出なくなる。これでよいか。
   - よくない場合は、練習モードのときだけ排他にする案がある。
3. Nano Cortex の入力「1+2」と「3+4」のどちらが DI か。弾いて確認したい。

## 6. まだ計測していないこと(手順)

- **実機の往復遅延**:出力から入力へケーブルを挿す(またはオーディオ機器のループバック機能を使う)。そのうえで次を実行する。
  ```
  crates/tabstudio-audio/target/release/examples/live_probe.exe loopback --in "<入力名>" --out "<出力名>" --seconds 10
  ```
  - 0.5 秒ごとに大きめのクリックが出るので、音量を下げておくこと。
- **8時間の連続稼働テストと、機器の抜き差しテスト**:フェーズ2で入力ストリームができてからスクリプト化する。
