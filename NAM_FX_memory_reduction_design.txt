NAM / 外部Audio FX メモリ削減設計
作成日: 2026-10-08
対象: C:\Users\takeu\Desktop\tab editor
状態: 主要なメモリ削減策を実装済み。後述の未着手項目は測定を踏まえて優先度を下げた。
目的: 音色、奏法、保存したFX設定、再生の安定性を維持しながら、常駐量と読み込み時ピークを減らす。
読み手: 後続の実装担当エージェント。ユーザーへ詳細説明を要求せず、この資料から調査・実装を再開できること。

1. 判断の要約

優先順位は、計測 → 不要な実体の解放 → Guitar DIの重複読み込み削減 → IPCの上限管理 → データ共有。
NAMの演算を軽量モデルへ変更したり、音声の品質を落としたりすることを初手にしない。

最も大きな候補はGuitar DIのサンプル常駐である。NAMや外部FXをギタートラックに追加すると、音源もGuitar DIへ切り替わるため、「NAM/FXが重い」という見え方でもサンプラーが主要因の可能性がある。
一方、外部プラグイン自身のメモリは製品依存であり、BIAS FX2が主因かどうかはプロセス別の差分計測まで断定しない。
削減率や削減MB数は現時点で保証しない。

2. 今回、実際に確認したこと

A. Guitar DI / SFZ
- native/sfz-host.py はStandard Guitar音源について起動時に6個のsfizz synthを作成する。
- 各synthに同一の13奏法をまとめたSFZを読み込む。弦別のベンドやスライドを独立させるための構成。
- イベントに応じて7～12番のlaneも追加生成しうる。6固定という前提で上限を決めない。
- preloadは既に8192。以前の65536へ戻さない。これ以上小さくする案にはディスク読み込みと音切れの検証が必要。
- 13ファイルのregion数合計は2514。これは参照定義数であり、ユニークサンプル数や常駐バイト数ではない。
- electron/fx-host.cjs はSFZロードごとに別Pythonプロセスを起動する。通常はGuitar DIトラックごとに1プロセス、その中に6弦分のsynth。
- 同一ファイルのデコード済みサンプルがsynth間で共有されるかは未確認。コード上の重複ロード回数をそのまま実メモリの倍率と断定しない。

B. NAM
- public/nam/nam-worklet.js のmodulePromiseにより、同一AudioWorkletGlobalScopeではWASMエンジンを共有済み。トラックごとのWASM丸ごと複製という前提は誤り。
- トラックごとにNAMのinstanceIdとモデル状態を持つ。
- 配布WASMのmemory sectionを読み取った結果: 初期1024ページ=64MiB、上限8192ページ=512MiB。
  これは線形メモリの仕様。64MiBがすべて実常駐するとは限らず、512MiBを常時消費する意味でもない。
- WASMファイルは415269 bytes。調査した工場出荷モデルは1ファイル約294～310KB。ファイルサイズとロード後の使用量は別。
- NAM OFF時、configure()は接続を外すがg.namとロードしたモデルを保持する。dispose()ではdestroyする。
- 無音時のNAM演算停止は既にあるが、CPU節約であってモデルメモリの解放ではない。
- トラックinitごとにwasmBytesをpostMessageで送る。共有エンジン初期化後の不要なバイト転送は減らせるが、最優先のGB級候補ではない。

C. 外部FX / IPC
- FXスロット1個につきPythonプロセス1個とプラグインインスタンス1個。
- editorを閉じてもDSPは再生用に残る。これは正常。editor-closeだけでプロセスまで消してはいけない。
- FX削除/OFFはconfigure()でclose対象になる。既にある解放経路を実測し、どこでも解放されないと誤認しない。
- エディターはプラグイン自身のネイティブウィンドウを使う。黒画面対策として512フレームの初期DSP処理もある。これらをメモリ削減のために安易に削除しない。
- renderer→Electron main→Python間でPCMをBase64/JSON化し、numpy配列へのコピーも発生する。
- FxHost.ask()はpending数の上限がなく、stdin.write()の戻り値によるバックプレッシャーもない。
  タイムアウトでpendingから外れても、既に送った処理は子側でキャンセルされない。遅いFXでの蓄積を要検証。
- public/native-fx.js は停止用destroyプロトコルがなくprocess()がtrueを返し続ける。
  port.close()/disconnectだけで実体が回収されるかを測定する。漏洩を断定はしない。

D. 譜面・タブ・保存
- MixerAudioは単一のgraphs配列を持ち、Score/track indexに紐づけて使用している。
- setScore()のみでは旧graphを解放しない。prepare()まで旧サンプラー/FXが残る経路を調査する。
- 非アクティブな全タブに独立した音声graphを常時保持している設計ではない。まず実際の所有者と切替タイミングを整理する。
- custom NAMのmodelJsonと外部FXのstateはtrackAudioに含まれ、attachAudioData()でstructuredCloneされる。
- NAMライブラリのプリセットはmodelJsonを複製しない設計が既にある。
- 履歴はMap/Arrayの共有を行うが、すべての音声設定オブジェクトが完全共有されるわけではない。
  同じ文字列が物理的に何倍になるかはJS実装と経路次第。heap snapshotで確認する。

E. 計測結果と限界
Windows上でGuitar DIをロードし、子PythonプロセスのPrivate Bytes / Working Setを測定した。
同一環境・同一音源・起動後1秒の比較:
- 1弦の全音程: 約1017MiB / 約652MiB。
- 1弦の指定3音程: 約455MiB / 約92MiB。
- 6弦の全音程: 約4223MiB / 約3762MiB。
- 6弦、各弦3音程: 約834MiB / 約384MiB。
比較条件は人工的な小規模譜面であり、一般の曲で同じ削減率を保証しない。NAM・BIAS本体の増減、長時間の安定後メモリ、OSキャッシュとの境界は未測定。

3. 実装前に作る計測

最初に開発用の音声リソース台帳を用意する。製品画面へ技術情報を大量表示する必要はない。
記録項目:
- document runtime ID / stable track ID / effect ID / generation / process PID / resource type。
- PythonのPrivate BytesとWorking Set、Electron main/renderer/GPUの同指標。
- NAM instance数、モデル別ロード数、WASM heap.byteLength、ロード時間。
- sfizz synth数、弦lane、奏法セット、preload、可能ならサンプルメモリ統計。
- IPC送受信bytes、in-flight数、待ち行列長、最古要求の年齢。
- underrunFrames、FXの遅延dry fallback回数、再生開始所要時間。

測定シナリオ:
1) 空譜面/GMのみを基準にする。
2) Guitar DIのみを1/2/4トラック。
3) 2にNAMを追加。次にNAMなしでBIASを追加。最後にNAM+BIAS。
4) editorを閉じた状態/開いた状態/閉じた後。
5) 再生中/停止直後/30秒後/60秒後。
6) ON/OFF、削除、プリセット切替、タブ往復を各20回。
7) 30分再生、密な奏法、6弦同時、7～12laneが必要な譜面。

各ケースを新規プロセスのcold状態と再利用warm状態で分ける。同じ譜面・レート・設定で比較。
Working Set合計だけでは共有ページを重複計上するので、Private Bytesも併記する。
OSキャッシュ、WASM予約領域、実常駐、JS heap、GPU使用量を混同しない。
削減効果はプロセス群全体の差分、最大値、安定後の値を報告する。

4. 第一段階: 所有関係と解放を確実にする

AudioResourceManagerを設け、設定データと動作中の実体を分離する。
キーはdocument runtime ID + stable track ID + FX ID。track indexのみを所有権に使わない。
文書切替やUndoでScoreオブジェクトが置換されても、設定を別譜面に保存しないこと。

状態案:
UNLOADED → LOADING → READY → ACTIVE → IDLE → RELEASING → UNLOADED
ERROR / generation mismatchも定義する。

解放方針:
- FX削除/トラック削除/譜面を閉じる: 必要なstateの保存後、対応実体を確実に解放。
- NAM OFF: モデルをunload/destroyして参照を外す。短時間の切替用猶予は停止中のみ、暫定5秒以下。
- 停止: すぐ全破棄せず30秒程度の猶予を候補とし、操作応答とメモリを比較して決定。
- 非アクティブ譜面: 設定・履歴・保存stateを維持し、実体は原則解放。切替元state取得完了後に所有者を移す。
- ミュート/ソロ除外: 再生中の即時アンロードは行わない。解除時の発音遅れ、エフェクトの残響、内部状態を保つ。
- メモリ不足時: 停止中の未使用実体から退避。保存state取得失敗時は黙って破棄しない。
- UIのNAM「有効」とruntime「ロード済み」を区別する。解放したからといってNAM設定をOFFへ書き換えない。

非同期の注意:
- LOADING中にタブを閉じても、後から完了したホストを必ず解放する。
- generationと所有者を確認してからgraphへ登録する。
- disposeを冪等にする。timer、pending、port、onmessage、native processを対で閉じる。
- NativeFx workletにdestroyを追加し、results/dry/block参照を外してprocess()をfalseにする。
- NAM destroy応答を待つ場合は期限を設け、その後portを閉じる。解除待ちの無期限保持を作らない。
- 保存/Undo/タブ切替/エディターを閉じる処理を直列化し、古いstateで新しい設定を上書きしない。

WASMに関する限界:
モデルをfreeしても線形メモリの高水位は下がらない可能性がある。
まず再利用により増加が止まるかを見る。OSへの返却が必要なら、全音声処理が停止し編集ウィンドウも閉じた境界でAudioContext世代を再生成する案を別途検証する。
再生成時はalphaTab出力、クリック、preview、namLoading/nativeModule/audioModulesなどのContext依存キャッシュをすべて再初期化する。NAMだけ部分的にContextを差し替えない。

5. 第二段階: Guitar DIの重複常駐を減らす

5.1 低リスク案: 必要なlaneだけ事前ロード
- 再生予定の譜面/MIDIから必要laneを収集し、再生開始前にまとめて作る。
- 6弦のうち2弦しか使わない譜面では残りをロードしない。
- 初回note-onで重いSFZロードを同期実行して音切れさせない。
- 編集による新しい弦、プレビュー、ループ/途中再生に備える。未準備時は読み込み表示を出して準備後に発音。
- 使用していないlaneの破棄は発音とrelease tailが終了した停止境界で実行。
- 全弦を使う譜面では効果が小さい。これだけで解決としない。

5.2 奏法セットを絞ったロード
- 必須の通常音/対応するreleaseを基本セットとし、譜面に必要なmute、harmonics、legato等を追加する案。
- keyswitchだけでなくベンド、grace/slide-in、アップストローク、note-offで選ばれるreleaseも依存として集計。
- sfizzへの差分追加APIが使えると仮定しない。使えない場合は停止中に必要セットを再構築。
- 未対応の奏法があればfullセットへフォールバック。音を黙って通常奏法へ置換しない。

5.3 本命候補: 不変サンプルデータ共有
- 同梱sfizzの実装/APIを調べ、synth間でデコード済みデータを既に共有しているか確認する。
- 共有していなければ、1つのサンプラーサービス内でサンプルキャッシュを共有し、弦/トラックのvoice、CC、pitch、keyswitchは独立させる設計を検討。
- 単に全弦を1 synthへまとめるだけでは、独立ベンドの互換性が壊れるので不採用。
- 同一プロセスに複数synthを置くだけでも共有されるとは限らない。必要ならsfizz側の変更コスト/ライセンス/更新方法を見積もる。
- 共有キーにはcanonical path、ファイル世代、デコード形式を含める。参照中のサンプルを追い出さない。
- クロストラックの共有は、プロセス分離方針と障害範囲を合わせて評価する。

5.4 preload調整
8192を基準として4096/2048を比較する案は上記の後。
低速ストレージ、高サンプルレート、同時発音、UI操作中の読み込みも試験する。
既存の8192設定で音切れを避けた経緯を尊重し、使用RAMだけを理由に固定で下げない。

6. 第三段階: 外部FXの常駐数とIPCを制御する

先に上限管理:
- 1インスタンスあたりのprocess in-flight数と待ち行列に明示的な上限を設ける。
- 8192フレームの既存レイテンシと2048フレームの処理単位を基準に、必要最小の先行要求数を実測で決定。
- DSP入力を無造作に間引かない。プラグインの内部状態が変わるため、過負荷時は現行dry fallbackから段階的に退避し、停止/リセット/再準備へ遷移する。
- ノードを破棄した後の応答や古いepochを捨て、process promiseが実体を保持し続けないようにする。
- stdinのバックプレッシャーを扱う。timeoutだけで子側の積み残しを解決したつもりにならない。

その後、Base64/JSON PCMをバイナリ転送へ:
- 制御メッセージとPCMフレームを分離。長さ、instance ID、request ID、epoch、rate、frames、channel countをヘッダーに持たせる。
- 部分read/write、クラッシュ、フレームサイズ上限、リトルエンディアンを定義。
- Python側の入出力配列は再利用。SFZのleft/right/pcmも処理サイズ上限内で再利用する。
- Electron IPCのコピーも計測し、必要ならMessagePortや共有リングバッファを検討する。
- 共有メモリは所有権と同期が難しく、初手にしない。効果は常駐サンプル量よりGC/瞬間ピーク/CPUの改善が中心の可能性。

FXホストのプロセス集約は後回し:
- Python/numpy等の基礎コストは減る可能性があるが、BIAS本体の各インスタンスのメモリは残る。
- 全FXを1プロセスにすると1個のクラッシュが全音声へ波及し、複数editorのメインスレッド制約も生じる。
- 当面は個別ホストを維持し、停止中の退避とロード数管理を優先。

7. 第四段階: モデル/保存stateを参照化する

- custom NAMは内容hashをキーにした不変AssetStoreへ1回格納する。
- track/preset/historyはhashとパラメーターを持つ。同じNAMでもDSPの時系列状態はトラックごとに独立させる。
- 外部FXのstateも内容hashごとの不変blobとして管理し、変更時だけ新しいblobを作る。
- project/既存TGの書き出し時は必要な実データを含め、別PCへ持ち運べる状態を維持する。
- 既存のmodelJson/state埋め込み形式から読み込める移行処理と、Undo/Redo・復旧データ・コピー&ペーストを検証する。
- UIでライブラリを開くたびに全モデルJSONを読む方式は、メタデータ一覧とモデル本体の遅延取得に分離する。
- NAM init後の不要なwasmBytes再送をなくす。エンジン共有は既にあるので作り直さない。

8. 初期案として採用しないこと

- NAMのslimSize変更、サンプルレート低下、モノラル化による音質変更。
- 先読み65536/prime32768やFX_LATENCY8192の単純縮小。
  65536フレームのfloat32 stereo PCMは1出力あたり約0.5MiB。多重コピーは別途計測するが、先読み削減だけでGB級問題を解決する計画にしない。
- 正常な同時発音を切る、releaseを省く、弦別ベンドをまとめる。
- 再生中に全プロセスを強制終了する、ユーザーのFX設定を失ったまま退避する。
- Task ManagerのWorking Setだけを下げる強制トリミングを解決策とする。
- 同じモデルだからといって複数トラックのNAM/FX演算を1つへ共有する。アンプは非線形かつ状態を持つ。
- WASM初期64MiBだけを減らせば全体問題が解決すると決める。再ビルドする場合も別フェーズ。

9. 実装順と完了条件

Phase 0: リソース台帳と測定。最大消費元を確定し、優先順位を必要なら入れ替える。
Phase 1: runtime所有者、解放、ロードキャンセル、worklet終了、停止中退避。
Phase 2: Guitar DI lane事前解析 → 必要奏法ロード → サンプル共有可否の調査/試作。
Phase 3: IPC上限とバックプレッシャー → バイナリ化/配列再利用。
Phase 4: モデル/FX stateの参照化。必要な場合だけContext再生成・ホスト集約を別途設計。

受け入れ条件:
- OFF/削除/閉じた譜面の実体数が設計どおり減り、20回繰り返しても生存数が増えない。
- メモリは初期化による高水位到達とリークを区別し、warm状態で増加が収束すること。
- inactive譜面に実体を残さなくても、復帰時に音源/モデル/FX順序/設定が一致する。
- 途中再生、クリック、ループ、スライドインの到達音、トリル、独立ベンド、アップストロークを維持。
- BIASを追加後に自動で開く操作、3回以上の再オープン、黒画面対策を維持。
- 同じ条件の30分再生でunderrunやfallbackが現状より悪化しない。
- 全既存テストに加えて、解放後の再ロード、ロード途中のタブ閉鎖、state保存失敗、子プロセス停止を検証。
- 1/2/4トラックのPrivate Bytesとピークの比較を残し、どこが何MiB減ったかを説明できる。

実装状況 (2026-10-08):
- Phase 0: MixerAudio.resourceStats()とFxHost.stats()を追加。SFZ子プロセスのPrivate Bytes/Working Setを実測。
- Phase 1: 譜面切替時にFX状態を取得してNAM/SFZ/外部FXを解放。NAM OFF時はモデルをdestroy。外部FX workletにdestroyを追加。ロード中の操作はoperationキューで順序管理。
- Phase 2: MIDIの奏法メタデータから弦と音程を抽出し、SFZの該当regionだけを読み込む。譜面編集で弦/音程が増減した場合は停止中に再準備。未知の音程は再生時にも追加して音を欠落させない。全音程版との単音波形は完全一致。
- Phase 3: 外部FXに24要求の同時処理上限とstdinのバックプレッシャー検知を追加。過負荷では既存の遅延dry fallbackを使い、再生を止めない。
- Phase 4 (一部): 編集履歴の未変更なNAM/FX設定オブジェクトを共有。従来形式の保存互換性を維持。
- 再生前NAM/FX: 譜面のMIDI生成後から非同期で読み込む。準備中は再生ボタンに表示し、準備が終わるまで押せない。
- 検証: 164件のユニットテスト、NAM+BIASの事前ロード/譜面切替解放、弦追加/削除、2トラックNAM+BIASの継続再生とFX操作を確認。

未着手・条件付きの案:
- SFZのsynth/トラック間サンプルキャッシュ共有は同梱sfizzの共有可否確認が必要。音程限定で大幅に削減できたため先に導入しない。
- PCMのバイナリ転送、プロセス集約、保存stateのhash参照化はメモリ主因ではない可能性が高く、今回の実測と回帰リスクを踏まえて保留。
- NAMのWASM線形メモリは全トラックで共有済み。全NAM解放後もAudioContextの高水位は残りうる。Context全体の再生成はオーディオ時計を含む全経路の再構築が必要で、現時点では実装しない。
- 停止中の時間制限付きアンロードは、再生ボタンでのNAM再読み込み待ちを再発させるため採用しない。

一般の実譜面とBIASの組合せで、1/2/4トラック・30分再生のプロセス別メモリを再計測する。Working Setがなお過大な場合だけサンプル共有を検討する。
